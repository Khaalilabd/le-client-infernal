## 5.1 Module 1 — Générateur de clients

**Responsable :** Khalil Abdelmoumen · **Branche :** `feature/client-generator` · **Dossiers :** `server/src/modules/client-generator/`, `client/src/modules/client-generator/` · **Version :** 0.2

### Objectif et fonctionnalités

Le module 1 génère, grâce au LLM, le **scénario** sur lequel repose toute une séance : un client fictif, sa personnalité, le contexte de son organisation, ce qu'il demande (besoin exprimé), son vrai problème (besoin caché) et ses contraintes implicites. C'est la donnée d'entrée des modules 2, 3, 4 et 5.

| Fonctionnalité | Réalisation |
|---|---|
| Choix du domaine | Saisie libre et 12 domaines suggérés (santé, éducation, logistique…) |
| Choix du niveau | Débutant, intermédiaire, avancé, avec une description de chaque niveau |
| Choix de la personnalité | 6 profils (coopératif, pressé, méfiant, bavard, contradictoire, indécis) ou « aléatoire », tiré au sort par le serveur |
| Génération par l'IA | Prompt système v0.2, réponse validée par un schéma Zod dépendant du niveau |
| Stockage et consultation | Liste filtrable (domaine, niveau, personnalité), page de détail publique, état vide |
| Suppression | Réservée à l'enseignant ; refusée (409) si des séances utilisent le scénario |
| Mode sans clé API | Réponses simulées variées : 5 familles de domaines + mode générique, 6 profils, 3 niveaux |
Tableau : Fonctionnalités du module 1

| Méthode | Route | Rôle | Rôle de l'endpoint |
|---|---|---|---|
| GET | /api/client-generator/options | connecté | Domaines suggérés, niveaux et profils de personnalité |
| POST | /api/client-generator/scenarios | connecté | Génère et enregistre un scénario (version publique renvoyée) |
| GET | /api/client-generator/scenarios | connecté | Liste filtrée par domaine, niveau et personnalité |
| GET | /api/client-generator/scenarios/:id | connecté | Détail public d'un scénario |
| DELETE | /api/client-generator/scenarios/:id | enseignant | Suppression (refusée si le scénario est utilisé) |
Tableau : Endpoints du module 1

Le profil de personnalité est stocké dans le champ JSON `personality` du scénario : la fonctionnalité a été ajoutée **sans modifier le schéma de la base**, donc sans impact sur les autres modules.

### Prompts utilisés

Deux types de prompts interviennent dans ce module : les prompts de développement adressés à l'assistant (journal des prompts) et le prompt système utilisé par l'application elle-même pour générer les scénarios.

| Prompt | Type | Rôle |
|---|---|---|
| P-001 | Développement | Squelette du module et première version (v0.1) du prompt système |
| P-004 | Développement | Rédaction, avec l'IA, du prompt de développement du module |
| P-005 | Développement | Version complète du module (voir section 2.8) |
| generate-scenario.md | Système (application) | Génération d'un scénario au format JSON ; v0.1 puis v0.2 |
| level-*.md (3 fichiers) | Système (fragments) | Règles de difficulté propres à chaque niveau, injectées dans le prompt principal |
Tableau : Prompts liés au module 1

| Aspect | Prompt système v0.1 (P-001) | Prompt système v0.2 (P-005) |
|---|---|---|
| Personnalité | Inventée librement par le LLM | Imposée : profil choisi et comportement attendu |
| Difficulté | Trois lignes génériques | Règles détaillées par niveau (fragments level-*.md) |
| Besoin caché | Doit être découvrable | Doit découler du contexte, être découvrable par des questions précises et décrire son impact concret |
| Doublons | Non gérés | Titres existants du domaine fournis au LLM |
| Validation Zod | Format seul | Besoin caché différent du besoin exprimé ; nombre de contraintes conforme au niveau |
Tableau : Évolution du prompt système du module 1

Si la réponse du LLM ne respecte pas ces règles, elle est rejetée par Zod et le service IA partagé relance automatiquement l'appel : la qualité est garantie par le code, pas seulement par la formulation du prompt.

### Tests

Le module est couvert par **18 tests automatisés**, exécutés avec les 13 tests de la base commune (31 tests au total, tous réussis) :

- validation des schémas : profil inconnu refusé, besoin caché identique au besoin exprimé refusé, nombre de contraintes contrôlé pour chaque niveau ;
- réponses simulées conformes au schéma pour les **108 combinaisons** domaine × niveau × personnalité ;
- construction du prompt v0.2 sans variable manquante ;
- endpoints testés sur une vraie base : authentification, validation, filtres, rôles (403 pour un étudiant qui supprime), refus de suppression (409), et **absence du besoin caché et des contraintes implicites dans toutes les réponses**, sans compter sur le filtre de sécurité.

### Difficultés et apport de l'IA

- **Couplage caché entre tests** : des tests de la base commune utilisaient le prompt du module 1 comme exemple et ont échoué avec la v0.2. L'IA a demandé l'accord du chef de projet avant de toucher au code partagé, puis a découplé les tests : chaque membre peut désormais faire évoluer ses prompts sans casser les tests communs.
- **Mode simulé peu crédible** : pour un domaine sans gabarit dédié (ex. Tourisme), la réponse simulée ne mentionnait pas le domaine. Le défaut a été repéré en vérifiant l'écran dans un navigateur, puis corrigé.
- **Décisions humaines** : refus de suppression d'un scénario utilisé, génération ouverte aux deux rôles, découplage des tests. Ces choix sont tracés dans le journal des prompts.

### Limites et perspectives

- Le prompt système v0.2 n'a pas encore été évalué avec un vrai fournisseur (Claude ou OpenAI), faute de clé API.
- Le mode simulé ne propose que deux situations par famille de domaine : les titres se répètent après deux générations dans le même domaine.
- La liste n'est pas paginée.
> À compléter : après un test avec un vrai fournisseur, ajouter un exemple de scénario généré et comparer sa qualité à celle du mode simulé.
